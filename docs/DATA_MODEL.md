# Data model

All data is JSON, with one file per record. Fields marked **derived** are never stored. The build computes them from chapter files.

The examples on this page are illustrative placeholders (a lighthouse story with characters `mara` and `tobias`). They are not facts from your books.

## The accuracy contract

These rules apply to every file in `data/` and are enforced by the build where possible.

1. **Every statement has a source.** Each fact, each sentence of AI-written prose (summaries, synopses, arcs, notes on traits and relationships) and each profile value carries at least one **ref** naming the file, the chapter (or sheet row) and a verbatim quote. A statement with no ref fails the build.
2. **Unknown means empty.** If the text doesn't state something, the field is `null` (or `[]`). Nothing is guessed, typical-for-the-genre, or "probably". The app shows empty fields as *Not mentioned*.
3. **Provenance is visible.** The app shows the book and file, the chapter and the quote next to every statement. Inferred or implied information is visibly labeled as such.
4. **Contradictions are kept, never resolved.** When sources disagree, every version is stored with its refs (see *Disputed values*), and an entry goes into `contradictions.json`. No source has precedence over another.

## Layout

```
config.json                 project name, books, posts, sheet, heading words (see docs/CONFIGURATION.md)
source/                     author-owned: book1.md or book1.docx, book2…, sheet.csv (optional),
                            posts/ (supplementary documents, .docx or .md). See source/README.md
text/                       generated by tools/extract.mjs: book1.md, posts/<name>.md (never hand-edited)
planning/                   author-owned plans and outlines. NOT a source: never parsed or cited
data/
  meta.json                 last parsed commit, schema version
  chapters/b1-c03.json      evidence layer: one per chapter, prologue, epilogue or interlude (and one per post)
  characters/<id>.json      registries: identity + synthesis + author fields
  places/<id>.json
  events/<id>.json
  groups/<id>.json          institutions, factions, families, crews, companies
  lore/<id>.json            magic, rules, creatures, customs, calendars, terms
  threads/<id>.json         plot threads: mysteries, promises, setups (open or resolved)
  contradictions.json       every disagreement between passages or sources
media/<type>/<id>.<ext>     images (see media/README.md)
tools/extract.mjs           source/ (.md or .docx) → normalized text/ mirror
tools/build.mjs             data/ + text/ → app/db.js + app/text.js (validate, derive, bundle)
tools/query.mjs             read-only search over the built DB and text/
app/                        the web app. app/db.js, app/text.js, app/manifest.webmanifest and app/media/ are build output
```

## IDs

- **Entities** use lowercase kebab-case slugs of the most common name: `mara`, `tobias`, `gull-point-lighthouse`, `harbour-board`. IDs are permanent. Renames go in `name`/`aliases`, and the ID stays.
- **Chapters** use `b<book>-c<nn>`, for example `b1-c03` or `b2-c47`. A prologue is `b1-prologue`, an epilogue `b1-epilogue`, and interludes `b1-interlude-1`, `b1-interlude-2` (by their own number, or counted in order when unnumbered). The build works out these IDs and the reading order from the headings in `text/`. See `tools/lib.mjs`.
- **Posts** use their `config.json` key, which starts with `post-`: `post-world-guide`.
- **Events** use a descriptive slug, with a book prefix only when it's needed to disambiguate: `the-storm`, `the-trial`, `the-trial-day-1`, `harbour-fire`.
- An ID is unique within its type.

## Refs (sources)

There are three kinds of ref.

**Manuscript ref**
```json
{ "file": "book1", "ch": "b1-c03", "quote": "her brown hair, still damp from the rain" }
```
- `file` is the key from `config.json` (`book1` is `source/book1.md`, normalized into `text/book1.md`). It must match the book in `ch`, and the build checks this.
- `quote` is copied **verbatim** from that chapter of the text mirror. It is 4 to 30 words long, and the shortest span that proves the statement and is unique in the chapter.
- Before matching, the build normalizes whitespace, curly and straight quotes, dashes, ellipses (`…` and `...`) and `*` italic markers, and is case-insensitive. Nothing else is fuzzy.

**Post ref**
```json
{ "file": "post-world-guide", "ch": "post-world-guide", "quote": "The Board meets on the first Monday." }
```
- A **post** is a supplementary source the author publishes outside the books, such as a lore post, a bonus scene or an author's note. It is one section with no chapters, so its `ch` is its own file key. Quotes follow the same rules as manuscript quotes, checked against the post's text mirror.
- A post has no precedence over the books or the sheet. Where it disagrees with them, the disagreement goes to `contradictions.json` like any other.
- Posts written in a character's voice (a diary, a letter) are in-world documents: their facts use `voice: "document"` with that character as `speaker`, and world claims carry `basis: "claim"`.

**Sheet ref** (only if the project has a planning sheet)
```json
{ "file": "sheet", "row": 5, "cells": ["Mara", "16"] }
```
- `row` is the 1-based line number in the sheet CSV, and `cells` are exact cell values that must all be present in that row.

**Shorthand inside chapter files.** A fact or event portion in a chapter file carries only `"quote"`. Its `file` and `ch` are the chapter's own, and the build expands it into a full ref. Everywhere else, refs are written out in full.

The app renders a ref as **Book 1 (book1.md) · Ch 3 "The Letter": "…quote…"**, **Post (world-guide.md) · title**, or **Sheet (sheet.csv) · row 5**.

## Sourced values

Single values that aren't plain identity (dates, profile entries, a place's parent) use this shape:

```json
{ "value": "brown", "refs": [ { "file": "book1", "ch": "b1-c03", "quote": "…" } ] }
```

The field is `null` when the sources don't state it. `"basis"` is an optional key with one of three values:
- `"stated"` (the default) means it is said outright.
- `"implied"` means a quoted passage directly shows it without saying it. The app labels it *implied*.
- `"inferred"` is only for arithmetic from quoted cues, such as "three days after the 12th". The refs must include every cue used, and the app labels it *inferred*.

## Disputed values

When sources disagree about a single value (hair colour, a date, an age), the field doesn't pick one. It lists every version:

```json
"eyes": {
  "disputed": [
    { "value": "green", "refs": [ { "file": "book1", "ch": "b1-c04", "quote": "…" } ] },
    { "value": "hazel", "refs": [ { "file": "book2", "ch": "b2-c10", "quote": "…" } ] }
  ],
  "contradiction": "mara-eye-colour"
}
```

- The versions are listed in chapter order, and no version is primary.
- `contradiction` is the ID of the matching entry in `contradictions.json`, which must exist.
- The app shows all versions side by side with a *disputed* badge that links to the contradiction.
- A change the text **explains** (dyed hair, a new title) is not disputed. The value is the latest one, and the history lives in the derived facts.

## Sourced prose

All AI-written prose is stored as a list of sentences, each with its own refs:

```json
"summary": [
  { "text": "Mara arrives at the lighthouse on the night of the storm.", "refs": [ { "file": "book1", "ch": "b1-c11", "quote": "…" } ] },
  { "text": "She relights the lamp after the inquiry.", "refs": [ { "file": "book1", "ch": "b1-c22", "quote": "…" } ] }
]
```

A sentence may combine several refs. It may not contain any claim that none of its refs supports.

## Dates

Dates are ISO strings at any precision: `"1898"`, `"1898-07"` or `"1898-07-08"`. A date range is a sourced value:

```json
{ "start": "1898-03-11", "end": null, "basis": "stated", "refs": [ { "file": "book1", "ch": "b1-c03", "quote": "…" } ] }
```

`end` is `null` for a single day. Add `"approx": true` when the source itself is vague ("late summer"). If no source gives a date, `dates` is `null`. Nothing is estimated. If two passages (or the text and the sheet) give different dates, `dates` is disputed (see above).

A story with an invented calendar can still use this shape if the author maps it to numbers (record that mapping in `docs/PROJECT.md`). Otherwise leave `dates` `null` and keep the in-world date as a fact; the timeline then orders by chapter.

## `data/chapters/<chapter-id>.json`: evidence layer

These files are regenerated from scratch whenever the chapter text changes. They are never patched.

```json
{
  "id": "b1-c03",
  "book": 1,
  "file": "book1",
  "kind": "chapter",
  "number": 3,
  "sourceHash": null,
  "dates": { "start": "1898-03-11", "end": null, "refs": [ { "file": "book1", "ch": "b1-c03", "quote": "…" } ] },
  "pov": [ { "id": "mara", "quote": "…" } ],
  "summary": [
    { "text": "Mara receives a sealed letter at breakfast.", "quote": "…" }
  ],
  "sheetEvents": [ { "label": "Mara gets letter", "row": 4 } ],
  "sheetNotes": [],

  "appearances": [
    { "id": "mara", "type": "character", "presence": "on-page", "quote": "…" },
    { "id": "tobias", "type": "character", "presence": "mentioned", "quote": "…" },
    { "id": "gull-point-lighthouse", "type": "place", "presence": "on-page", "quote": "…" }
  ],

  "events": [
    {
      "id": "the-letter",
      "part": "full",
      "summary": [ { "text": "…", "quote": "…" } ],
      "participants": [ { "id": "mara", "presence": "on-page", "role": "recipient", "quote": "…" } ],
      "places": [ { "id": "gull-point-lighthouse", "quote": "…" } ]
    }
  ],

  "facts": [
    { "about": ["mara"], "category": "appearance", "aspect": "hair",
      "text": "Mara has brown hair.", "quote": "her brown hair, still damp from the rain", "voice": "narration" },
    { "about": ["mara"], "category": "outfit",
      "text": "Mara wears a grey wool coat with brass buttons.", "quote": "…", "voice": "narration" },
    { "about": ["mara"], "category": "taste", "aspect": "food",
      "text": "Mara dislikes porridge.", "quote": "…", "voice": "thought", "speaker": "mara" },
    { "about": ["tobias", "mara"], "category": "relationship",
      "text": "Tobias says Mara cannot be trusted.", "quote": "\"You can't trust her,\" Tobias said",
      "voice": "dialogue", "speaker": "tobias", "basis": "claim" }
  ],

  "unregistered": [ { "name": "the ferryman", "quote": "…" } ],
  "flags": [
    { "kind": "unclear", "text": "Unclear whether 'the girl' here is Mara or her cousin.", "quote": "…" }
  ]
}
```

Every appearance, participant and place link carries a quote, so "Mara appears in chapter 3" is as verifiable as any fact.

**`sourceHash`** fingerprints the chapter text the file was extracted from. Whoever (re)writes a chapter file sets it to `null`. A successful `node tools/build.mjs` then stamps it with the hash of the current chapter text. A non-null hash that no longer matches the text means the chapter changed after extraction, so it is **stale**. Never copy or edit a hash by hand.

| Field | Notes |
|---|---|
| `kind` | `chapter`, `prologue`, `epilogue` or `interlude`, matching the heading in `text/`. `number` is the chapter (or interlude) number, and `null` for a prologue or epilogue. Post files have `"book": null`, `"number": null` and no `kind`. |
| `presence` | `on-page` (physically in the scene) or `mentioned` (talked or thought about). |
| `events[].part` | `full`, `start`, `continues` or `end`, for events that span chapters. |
| `facts[].category` | See the table below. |
| `facts[].aspect` | An optional free sub-label for grouping in the app: `hair`, `eyes`, `scar`, `food`, `music`, `childhood`… |
| `facts[].voice` | `narration`, `dialogue`, `thought` or `document` (letters, books, diaries). |
| `facts[].speaker` | Required when `voice` is `dialogue`, `thought` or `document`. |
| `facts[].basis` | `stated` (the default, can be omitted), `implied` (shown by the quoted passage but not said), `claim` (asserted by a character and not confirmed by narration) or `rumor`. |
| `unregistered` | Names that appear but have no registry entry yet. They are resolved after extraction. |
| `pov` | The viewpoint character or characters, each with a quote that shows it. The list is empty if the text doesn't make the viewpoint evident. |
| `sheetEvents`, `sheetNotes` | Only with a planning sheet: the sheet's event labels for this chapter, and cells that are notes rather than happenings, each with its row. Omit them (or leave them empty) otherwise. |
| `flags` | Only `kind: "unclear"`, for things the extractor couldn't decide and left out. They're shown to the author in the reparse report. Contradictions go to `contradictions.json`, never here. |

### Fact categories

| Category | For | Examples |
|---|---|---|
| `appearance` | characters | Hair, eyes, height, build, skin, scars, voice, smell. Aspect: `hair`, `eyes`… |
| `outfit` | characters | **Every** described outfit, uniform, jewelry, accessory or disguise costume, even if worn once. The app lists them by chapter. |
| `taste` | characters | Likes, dislikes, favorites, food, drink, music, books, colors, aversions, fears. |
| `habit` | characters | Mannerisms, routines, verbal tics, recurring gestures, vices. |
| `personality` | characters | Stated traits, and behavior that shows a trait (`basis: implied`). |
| `backstory` | characters, groups | Childhood, family history, past events, former roles, origin. |
| `relationship` | characters | Ties to other characters and how they change. `about` lists both. |
| `ability` | characters | Skills, magic, education, languages, limitations. |
| `status` | characters | Titles, occupation, rank, injuries, death, imprisonment, location changes. |
| `possession` | characters | Notable objects, property, pets, heirlooms. |
| `goal` | characters | Wants, plans, motivations, as stated. |
| `secret` | any | Things hidden from other characters (and who knows them). |
| `knowledge` | characters | Who knows, learns, remembers or forgets what: what someone is told, overhears, discovers or recognizes. |
| `deception` | characters | Lies, cover stories, disguises, false names, and who is deceived. Each lie is a fact with the liar as `speaker` and `basis: "claim"` (or `implied` when the narration shows it). |
| `description` | places, events | Look, layout, furnishings, atmosphere, smells, sounds. |
| `geography` | places | Location, distances, travel times, what's nearby. |
| `history` | places, groups, lore | Past of a place or institution. |
| `lore` | lore, groups | Rules, customs, how things work. |
| `other` | any | Anything concrete that fits nowhere else. |

## Registries

Registries hold identity, sourced structured values, sourced prose and author-owned fields. Fields not listed are not used. **Any sourced field without a source is `null` or `[]`.**

### `data/characters/<id>.json`

```json
{
  "id": "mara",
  "name": "Mara",
  "aliases": [ { "value": "Miss Vell", "refs": [ … ] } ],
  "role": "protagonist",
  "importance": "major",

  "profile": {
    "fullName":   { "value": "Mara Vell", "refs": [ … ] },
    "title":      null,
    "birthday":   null,
    "ageAtStart": { "value": 27, "refs": [ { "file": "book1", "ch": "b1-c01", "quote": "…" } ] },
    "origin":     null,
    "occupation": null,
    "hair":       { "value": "brown", "refs": [ { "file": "book1", "ch": "b1-c03", "quote": "…" } ] },
    "eyes":       null,
    "height":     null,
    "build":      null,
    "marks":      null,
    "status":     null
  },

  "groups": [ { "id": "harbour-board", "role": "member", "refs": [ … ] } ],

  "summary": [ { "text": "…", "refs": [ … ] } ],
  "personality": [
    { "trait": "Stubborn", "note": "Refuses to sell the tower despite warnings.", "basis": "implied",
      "refs": [ { "file": "book1", "ch": "b1-c14", "quote": "…" } ] }
  ],
  "relationships": [
    { "with": "tobias", "type": "godfather", "since": "b1-c02",
      "note": [ { "text": "…", "refs": [ … ] } ] }
  ],
  "arcs": [ { "book": 1, "text": [ { "text": "…", "refs": [ … ] } ] } ],

  "images": [ { "file": "mara.jpg", "caption": "Grey coat, B1 Ch1" } ],
  "notes": "Author-owned. AI never edits this."
}
```

- `role` and `importance` (`major`, `supporting` or `minor`) are **navigation labels**, not story facts. They need no ref, and the app doesn't present them as canon.
- Every `profile` key is always present. It is either a sourced value or `null`. A value that changed over time (dyed hair, a new title) keeps its latest form here, and the full history lives in the derived facts.
- Projects can add profile keys in `config.json` (`"extraProfileFields": { "species": "Species" }`). Each extra key must then be present in every character file too, as a sourced value or `null`.
- `status` stays `null` until the text states a lasting change. For a character who dies it becomes `{ "value": "dead", "since": "b1-c38", "refs": [the passage where it happens] }`. "Alive" is never asserted. The app shows "last seen" from the derived appearances instead.

**Derived:** chapter appearances (on-page and mentioned), first and last appearance, and every fact grouped by category and aspect. That includes an outfit list in chapter order, tastes, habits, backstory and the rest. Also derived: the events taken part in, places visited, and the reverse side of relationships.

### `data/places/<id>.json`

```json
{
  "id": "gull-point-lighthouse",
  "name": "Gull Point lighthouse",
  "aliases": [ { "value": "the tower", "refs": [ … ] } ],
  "type": "building",
  "parent": { "value": "saltmere", "refs": [ … ] },
  "summary": [ { "text": "…", "refs": [ … ] } ],
  "images": [],
  "notes": ""
}
```

`type` is a navigation label (`city`, `building`, `room`, `region`, `country`, `ship`…). `parent` is `null` unless the text places it inside another place.

**Derived:** description and geography facts, child places, the events held there, characters seen there, and the chapters set there.

### `data/events/<id>.json`

```json
{
  "id": "the-trial",
  "title": "The trial",
  "parent": null,
  "tags": ["trial"],
  "importance": "major",
  "dates": { "start": "1898-03-23", "end": "1898-03-27", "refs": [ … ] },
  "synopsis": [ { "text": "…", "refs": [ … ] } ],
  "causes":       [ { "id": "harbour-fire", "refs": [ … ] } ],
  "consequences": [],
  "images": [],
  "notes": ""
}
```

- `title`, `tags` and `importance` are navigation labels.
- An event that appears only in the planning sheet and is never depicted in the text keeps just its sheet refs, and the app shows it as *sheet only*. Future plans from the sheet are never recorded (see PARSING_GUIDE).
- `causes` and `consequences` need refs showing the link in the text. If the link isn't stated, they stay empty.

**Derived:** chapters (in order, with each chapter's portion of the summary), participants (combined from all chapters, with on-page versus mentioned), places and sub-events (via `parent`). An event's own `dates` are never filled from chapter dates, because a chapter can recall an earlier event.

### `data/groups/<id>.json` and `data/lore/<id>.json`

```json
{ "id": "tide-calendar", "name": "The tide calendar", "kind": "calendar",
  "aliases": [],
  "summary": [ { "text": "…", "refs": [ … ] } ],
  "details": [ { "label": "Spring tides", "value": "Twice a month, at the new and full moon",
                 "refs": [ { "file": "book1", "ch": "b1-c05", "quote": "…" } ] } ],
  "notes": "" }
```

Groups use `kind` values like `institution`, `faction`, `family`, `crew` or `religious-order`. Lore uses `kind` values like `magic`, `creature`, `custom`, `calendar`, `technology` or `term`. Members and mentions are derived the same way as for characters.

### `data/threads/<id>.json`: plot threads

```json
{
  "id": "who-lit-the-lamp",
  "kind": "mystery",
  "question": [ { "text": "Who lit the lamp on the night of the storm?", "refs": [ { "file": "book1", "ch": "b1-c01", "quote": "…" } ] } ],
  "about": ["gull-point-lighthouse"],
  "opened": "b1-c01",
  "developments": [
    { "ch": "b1-c12", "text": [ { "text": "…", "refs": [ … ] } ] }
  ],
  "status": "open",
  "resolution": null,
  "notes": ""
}
```

- `kind` is `mystery` (an unanswered question), `promise` (a stated plan, vow, deadline or deal), `setup` (an object, ability or fact the text draws deliberate attention to), `secret` (something hidden from other characters) or `conflict` (a stated rivalry or threat that is still active).
- `opened` is the chapter whose quote raises the thread. Each development is a later passage that moves the thread on.
- `status` is `open` or `resolved`. **`resolved` requires a `resolution`** (`{ "ch": "b1-c30", "text": [cited sentences] }`) quoting the passage that answers or closes the thread. Without that passage, the thread stays open.
- `notes` is author-owned. You can mark a thread there as deliberately left open, dropped and so on.
- `authorStatus` (optional, `null` or `"resolved"`) and `authorComment` (optional string) are author-owned. `"resolved"` means the author considers the thread closed even though the text doesn't resolve it. It needs no quote and no `resolution`, and it is independent of `status` (the text's own resolution). The AI never sets, changes or clears either field, and never uses them as a source. The app shows the thread as resolved, labelled "resolved by author", in every reader-knowledge mode.
- **Derived:** in reader-knowledge mode, a thread is visible from `opened`, and shows as resolved only from the chapter of its resolution.

## `data/contradictions.json`

```json
[
  {
    "id": "mara-eye-colour",
    "kind": "text-vs-text",
    "severity": "medium",
    "about": ["mara"],
    "text": "Mara's eyes are described as green in B1 Ch4 and hazel in B2 Ch10.",
    "sides": [
      { "claim": "green", "refs": [ { "file": "book1", "ch": "b1-c04", "quote": "…" } ] },
      { "claim": "hazel", "refs": [ { "file": "book2", "ch": "b2-c10", "quote": "…" } ] }
    ],
    "found": "2026-10-02",
    "status": "open",
    "authorComment": ""
  }
]
```

- `kind` is `text-vs-text`, `text-vs-sheet`, `sheet-vs-sheet` or `timeline` (impossible sequencing, travel or ages).
- `severity` is `low`, `medium` or `high`. It's a hint for sorting, not a judgment of which side is right.
- `status` is `open`, `intended` (the author says it's deliberate), `not-an-issue` (the author disagrees that it's a contradiction) or `resolved` (the text was changed so the sides now agree).
- **`status` values other than `open`/`resolved`, and `authorComment`, are author-owned.** The AI may move `open` to `resolved` only when a reparse shows the sides now agree, and it records the chapter where that happened.
- **Entries are never deleted.** A resolved or rejected contradiction stays listed as a reference. If one side's quote disappears because the text was edited, an `open` entry becomes `resolved`, and every closed entry keeps the old quote text for the record (the build checks quotes and sheet cells only on `open` entries).
- Every entry has at least two sides, and every side has refs.

## `data/meta.json`

```json
{ "schemaVersion": 1, "lastParsedCommit": "abc1234", "lastParsedAt": "2026-10-02", "lastParseScope": ["b1-c12", "b1-c14"] }
```

## `config.json`

See [CONFIGURATION.md](CONFIGURATION.md) for every key. The parts the data depends on:

```json
{
  "project": { "name": "Salt Lamp DB", "title": "The Salt Lamp", "description": "…" },
  "files": {
    "book1": { "book": 1, "title": "The Salt Lamp", "source": "source/book1.md", "text": "text/book1.md" },
    "sheet": { "source": "source/sheet.csv" },
    "post-world-guide": { "kind": "post", "title": "World guide",
                          "source": "source/posts/world-guide.docx", "text": "text/posts/world-guide.md", "after": "b1-c12" }
  }
}
```

A post's key starts with `post-`. `after` names the chapter a reader should have reached before the post: the build orders the post right after it, so reader-knowledge mode shows the post's facts from that chapter on. The post's evidence file is `data/chapters/<key>.json`, in the chapter-file shape with `"book": null` and `"number": null`.

## Build output (`app/db.js`, `app/text.js`, `app/manifest.webmanifest`)

```js
window.DB = {
  meta, project, files, chapters, characters, places, events, groups, lore, threads, contradictions,
  facts,          // flat list, each with a fully expanded ref
  index,          // derived lookups: appearancesById, eventsByPlace, factsByEntity…
  images          // id → [files] from media/
}
```

`app/text.js` holds the chapter text from `text/` for the reader view and the manuscript search, as `window.DB_TEXT = { "b1-c01": "…", … }`. It is a separate file so the app loads it only when it's needed. `app/manifest.webmanifest` (the phone install info) is generated from `config.json` `project`.

## Build checks

The build **fails** when:
- the JSON is invalid or a required field is missing,
- **any fact, appearance, participant, place link, prose sentence, sourced value, thread entry or contradiction side has no ref**,
- a disputed value has fewer than two versions, or points to a missing contradiction,
- a contradiction has fewer than two sides, or a thread is `resolved` without a cited `resolution`,
- a quote isn't found in its chapter of `text/` (it reports the file, the chapter, the quote and the closest match),
- a sheet ref's cells aren't all in that row,
- a ref's `file` doesn't match its chapter's book, or a referenced ID doesn't exist,
- a chapter file's `book`, `number`, `file` or `kind` doesn't match its heading, or two headings produce the same chapter ID,
- a `profile` key is missing (it must be a sourced value or `null`),
- `basis: "inferred"` is used on anything other than a date or number, or `speaker` is missing on dialogue, thought or document facts,
- a chapter exists in the source but has no chapter file, or the other way round.

The build **reports but does not fail** for:
- a book in `config.json` whose source file hasn't been uploaded yet,
- chapters whose `sourceHash` is stale (the reparse scope), and chapter files with `sourceHash: null` (which a successful build stamps),
- chapter files whose hash matches a *different* chapter (likely renumbering),
- registries with no remaining appearances, and a non-empty `unregistered` list,
- registries affected by the latest changes (the synthesis to-do list).

Run modes: `node tools/build.mjs` (full build, required for every commit), `--partial` (missing chapter files aren't errors, for checking work in progress), `--check` (scope report only) and `--list-chapters` (chapters in `text/`, with sheet dates if configured).

The build can prove a quote exists. It **can't** prove the quote means what the statement says. That is what the verification pass in [UPDATE_WORKFLOW.md](UPDATE_WORKFLOW.md) is for.
